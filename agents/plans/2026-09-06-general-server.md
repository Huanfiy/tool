# 执行计划：通用站点 Server，Robot 作为首个功能模块

- 日期：2026-09-06。
- 状态：**已搁置；用户明确暂停实现，仅保留供以后研究，不是当前执行任务。**
- 目标：一个精简、可扩展的站点后端，统一承载 `/api/`；Robot 只是其中一个模块。
- 优先级：干净、简洁、低操作成本，其次才是可配置性；不把“通用”做成插件平台或运维后台。
- 阅读说明：以下目录结构、命令、接口变化均为**目标设计，不代表当前已经实现**。

> **2026-09-06 基线更新：** 当前 Bot 功能已按要求清理，只保留 `studio.html` 中的「研究中」静态入口。原聊天/配置脚本、`server/`、`tools/robot/`、后端测试和运行说明已移除。下文保留制定计划时的设计与历史清单，不表示这些源码仍存在，也不是恢复功能的授权；以后重启研究时须重新盘点与修订，不能直接照搬旧迁移步骤。

## 1. 决策摘要

1. 网站继续使用原生 HTML/CSS/JavaScript，不增加前端框架、构建步骤或包管理器。
2. 新后端采用**模块化单体**：一个进程、一个监听入口、显式注册功能模块，不按功能启动多个服务。
3. 复用现有 Python/aiohttp 代码和固定依赖；本次不换语言、不换 Web 框架、不顺带升级依赖。当前依赖声明和已验证环境见 `server/requirements.txt`，Python 3.12 作为首轮验收基线；不要把旧安装器允许的最低版本当成已经验证的兼容范围。
4. 浏览器只请求本站 `/api/…`，站点 Server 再访问模型网关。Key 仅留在服务端，不进入网页、浏览器存储或公开源码。
5. Robot 固定渠道、模型、系统提示词和限制参数，不再提供屏内配置、配置密码、模型列表或配置管理 API。
6. 保留必要的安全和用量边界，不因删掉配置系统就变成匿名、无限额的通用中转。
7. 本地一个命令启动；生产一次安装后自动运行。通用开发、打包、安装代码放在仓库的 `tools/server/`，不再依赖个人目录。

本计划替代此前“前端内置 Key、调整网关 CORS 后直连”的候选路线。**修改外部模型网关的 CORS 不再是本站改造的前置条件**：网页到本站同源，Server 到网关是服务端 HTTP 请求。已有网关继续承担模型访问，不复制其渠道管理功能。

## 3. 架构与责任边界

### 3.1 请求路径

```text
生产：
浏览器 ──→ 既有网站入口 ──→ 静态文件
                     └──→ /api/… ──→ 通用 Server
                                        ├── 通用健康检查
                                        ├── Robot 模块 ──→ 现有模型网关
                                        └── 以后明确需要的其他模块

本地开发：
浏览器 ──→ 127.0.0.1:8080 的同一 Server 进程
              ├── 白名单静态资源
              └── /api/…（Robot 默认模拟，显式 --live 才调用模型）
```

生产前端仍按静态 Git Artifact 发布，不要求由 Python 接管整站。Server 默认仅监听回环地址；TLS、真实域名、代理、缓存和主机策略仍由运行环境管理。正式接入 `/api/` 前必须检查既有路由，不能盲目覆盖其他服务。

### 3.2 最小目录结构

```text
server/
  __init__.py
  __main__.py             # CLI 入口；没有依赖安装或系统服务管理
  app.py                  # 创建应用、组合公共资源、显式注册模块
  settings.py             # 通用启动参数、私有凭据读取校验工具
  web.py                  # API 错误/响应边界、共用的受控 HTTP 能力
  static.py               # 标准库可用的静态路径策略及纯静态预览
  requirements.txt        # 继续固定后端依赖
  modules/
    __init__.py
    robot/
      __init__.py         # 注册路由与模块资源
      api.py              # status/chat HTTP 与本站 SSE 协议
      service.py          # 固定渠道/模型、模块设置、上游请求与解析
      quota.py            # Robot 自有的计数/并发策略，不是全站数据库层

tools/server/
  dev.py                  # 项目内环境准备、开发启动、受控清理
  package.py              # 固定 Git 提交 → 通用后端包
  install.py              # 一次安装/升级/预览，不改未知站点配置
  README.md
```

目录是职责边界，不是要求每个函数单独建文件。小函数留在所属模块，不额外引入 controller/service/repository/interface 多层样板。

### 3.3 什么进入核心，什么不进入核心

- 核心负责启动、监听、通用设置、健康检查、API 错误响应、必要日志、公共 HTTP 资源、开发静态访问和资源清理。
- Robot 自己负责模型配置、消息协议、SSE、模拟回复、限额和模块状态。核心中间件不得访问 Robot 的数据库、Key 或模型字段。
- 公共 HTTP 客户端不得设置 Robot 的默认 Authorization 或保存 Cookie。Robot 仅在访问固定上游的那个请求上添加 Key，防止凭据随其他模块请求外流。
- 错误处理按 `/api/` 与静态响应区分；不能把 API 的 CSP 套到工作室页面，也不能把所有业务都假设为聊天/SSE。
- 使用 aiohttp 已有应用工厂、路由与 `cleanup_ctx` 等机制管理生命周期；不再套一层自制框架。初始化失败与正常关闭都要正确清理已经成功创建的资源。[R1]
- 模块通过普通注册函数挂入应用，拥有自己的状态和清理逻辑；不自动扫描目录、不加载用户指定 Python 模块、不允许 HTTP 请求动态安装功能。
- 模块边界不是进程级故障隔离。缺配置、上游失败等可预期问题按模块降级；不可恢复的核心/启动错误应明确失败，不能为显示“健康”而吞掉程序错误。

**扩展验收：** 测试中增加一个不依赖 Robot 的示例模块，只需模块代码、一个显式注册项和自身测试；无需修改启动/打包/安装逻辑或 Robot 文件。示例仅作测试夹具，不作为无需求的新业务发布。

## 4. 功能与接口契约

| 方法与路径 | 首期职责 |
| --- | --- |
| `GET /api/health` | 通用服务存活与 Git 版本；不请求模型，不返回配置、路径或秘密 |
| `GET /api/robot/status` | 公开 `enabled`、公开模型名及 `mode`；mode 区分 live/mock/disabled |
| `POST /api/robot/chat` | 仅接收受限的 `{messages:[{role,content}]}`，返回本站 SSE |
| 未来 `/api/<feature>/…` | 由该业务模块明确注册；默认不存在，不提前做空接口 |

- 保留现有 `delta`（text）、`done`、`error`（code/message）事件，减少客户端协议变化。流开始前按 HTTP 错误返回；流开始后用规范错误事件结束，不能再写第二份 JSON 响应头。
- 空回复、上游中途断流和错误不得伪装成 `done`；保留有边界的普通 JSON 回复兼容能力。
- 停止、清空、断开连接必须取消上游请求并释放连接、并发名额；应用关闭时有界等待/取消，不能遗留后台任务。
- 未配置 Key 时核心仍可启动；Robot 在生产中为 disabled，聊天返回明确的 503，不能悄悄使用模拟回复。已配置但失败的 Robot 应显示模块故障，不使其他功能必然失效。
- `/api/health` 成功不表示模型可用；`enabled` 只表示配置具备调用条件，不把它包装成实时渠道健康。
- 删除 `/api/robot/admin/*`、配置密码和模型管理接口；未知 API 返回明确 404，不退回 HTML 或通用代理。
- `/api/robot/health`、旧 CLI 和旧变量只在确有已安装实例时保留短期兼容，移除时间明确；不长期维护两套系统。

## 5. 配置、Key 与数据

### 5.1 简化设置，而不是公开秘密

- 渠道、模型和系统提示词放在 Robot 的服务端固定默认配置中；执行时先确认具体模型。若需覆盖，使用少量高级启动设置，不增加浏览器表单。
- 通用参数采用 `SITE_SERVER_*` 命名（Origin、状态目录、可信代理、解释器等）；Robot 的秘密采用模块命名空间，如 `SITE_ROBOT_API_KEY_FILE`。
- 不引入新的 dotenv/YAML 配置体系；优先复用环境注入和受保护文件。不存在“通过 source 执行配置文件”的做法。
- 普通使用不要求手动导出一串变量：开发工具给出安全默认值，生产安装流程写入私有运行参数；API Key 是站长需要提供的秘密。
- Key 不写入 HTML/JS、前端请求头、localStorage、URL、命令行参数、日志、Git 或静态产物；只在服务端私有配置/内存使用。[R2]
- 不自动读取 `tmp/testkey.txt`、旧浏览器设置、其他个人目录或旧 SQLite 中的 Key。
- 生产凭据只从明确配置的受保护来源读取；保留普通文件、所有者、权限、长度、符号链接及路径检查。拒绝把生产状态/凭据存进站点源码或公开目录。
- 旧 `STUDIO_ROBOT_PASSWORD` / `STUDIO_ROBOT_PASSWORD_FILE` 是配置密码，必须删除其职责，**不能误映射成模型 API Key**。

### 5.2 数据库只保留真实需要

通用核心不强制全站数据库，也不预建 ORM、用户表、配置中心或迁移框架。

Robot 当前有实际的匿名调用限额需求，因此保留小型 SQLite **用量计数**，但不再用它保存 Key、模型配置或聊天记录：

- 开发默认使用内存计数，不创建数据库文件。
- 生产保存在安装流程指定的私有状态目录下，例如模块子目录 `robot/quota.sqlite3`；这不是需要提交的目录或配置。
- 延续原子预占、失败/取消也计次、UTC 日界线、重启不重置每日次数的语义。
- 其他模块未来需要持久化时在自己的边界内实现；出现真实共享需求后才提取共用能力。

若实际存在旧实例，先备份私有状态，再经授权迁移计数。不能把包含 Key 的旧配置数据库整体复制到新代码包；旧文件不自动删除，旧数据也不自动上传。

## 6. 本地开发体验：一个入口，不污染系统

### 6.1 目标命令

```bash
./run.sh dev                 # 默认 8080，同源页面 + API；Robot 明确标注“模拟模式”
./run.sh dev 3000            # 自定义一个端口，不再分别起静态和 Robot 进程
./run.sh dev --live          # 真实模型；缺 Key 时在本机终端不回显输入，仅留内存
./run.sh dev --clean         # 清理本工具拥有的开发环境/缓存；运行中拒绝清理

./run.sh test [port]         # 保留纯静态预览，不安装 aiohttp、不启动 API
./run.sh server [port]       # API-only 运行入口，生产参数由托管环境一次注入
./run.sh server package [ref] # 通用后端 Git 产物，不自动提交或部署
```

默认模拟仅用于界面和流程开发，**不是正常模型聊天的替代证明**。真实聊天仍然需要可用网关、模型、网络和 Key；不能承诺免密钥、离线运行真实模型。

### 6.2 自动化边界

- `tools/server/dev.py` 自动创建/复用项目专用 `.venv/server/`；首次或固定依赖变化时才安装依赖，重复启动不反复下载。
- 可再生缓存/临时构建文件限制在 `tmp/server-dev/`，源码字节码写入受控或关闭；不使用之前准备的个人目录或外部测试虚拟环境作为运行依赖。
- 不修改系统 Python、全局 pip 配置、shell 启动文件，不注册 systemd、不调用 sudo。已有 Python/venv 能力不足、无网络或无适配依赖时明确失败，不自动安装操作系统组件。
- 使用隔离的依赖安装参数与受控缓存，忽略会把安装重定向到全局目录的配置；验证依赖环境身份、固定版本及准备锁，防止并发启动损坏环境。[R3][R4]
- 最终 Server 进程在 `--live` 且未显式提供私有凭据源时读入 Key，直接交给模块；不回显、不落盘、不经命令行传递。不在非交互环境等待输入，而是给出清楚错误。
- 默认模拟模式不读取真实 Key、不沿用生产 Origin/可信代理/状态目录、不访问上游；即使父环境已有生产设置，也不能隐式产生付费请求。
- 生产配置/真实 Key 不落项目目录；默认开发没有此类持久文件。这样依赖和可清理缓存留在项目内，同时不为“都放项目里”而放松秘密边界。
- Ctrl+C 停止唯一服务进程并清理其临时资源；不留守护进程。清理命令只删除有所有权标记的专用目录，拒绝链接/错误目录，不删除用户数据。
- venv 是依赖隔离，不是操作系统权限沙箱；不要声称绝对无法触及宿主环境。

### 6.3 静态文件访问

`dev` 和纯静态 `test` 共享一套基于标准库的路径决策，后者不能因为导入共享策略而强制安装 aiohttp。

- 仅开放站点页面、明确静态资源及测试模式允许的浏览器测试资源。
- 拒绝 `server/`、`tools/server/`、迁移期的 `tools/robot/`、`agents/`、`.git/`、`.venv/`、`tmp/`、`build/`、隐藏文件、凭据与数据库。
- 同时校验请求路径与解析后的实际路径，覆盖编码、目录穿越、符号链接和目录索引；正常网页工具和媒体资源不受影响。
- `.gitignore` 不等于 HTTP 访问控制，也不等于发布排除，三者分别验证。

## 7. 保留的安全底线

1. **终端永远是浏览器模拟。** 通用 Server 不得新增 shell、PTY、终端 socket、命令执行、任意文件读写或任意 URL 代理。安装/依赖准备中的进程操作只在离线 CLI 工具中，不由 HTTP 调用。
2. Robot 的请求不可覆盖 URL、Key、模型、系统提示词、工具或函数。模型没有操作主机、文件或真实设备的权限。
3. 继续校验固定公网 HTTPS 上游及实际 DNS 连接地址；拒绝内网/回环/混合解析、重定向和环境代理导致的凭据外流。测试使用注入的假客户端，不为生产新增“允许任意内网目标”的开关。
4. 暂沿用已有保守上限：请求体 64 KiB、最多 20 条消息、每条 4000 字符、合计 16000 字符、回复 32768 字符、上游数据 2 MiB；每来源 8 次/分钟、全局 40 次/分钟、3 个上游并发、默认每天 200 次尝试、最大输出默认 1024 Token。
5. 保留连接、读空闲和总请求超时以及完整取消。频率/并发为单进程策略，首期只运行一个实例；不能未经改造就宣称可多副本横向扩容。
6. 次数/Token 限制不是精确费用封顶。用网站专用网关 Key，配置并验证渠道侧实际额度约束；隐藏 Key 也不等于公开聊天接口不会被刷。
7. API 错误与日志不得泄漏 Key、完整请求头、消息正文、配置或上游错误正文；日志仅保留有助定位的非敏感状态/耗时/模块信息。
8. Origin 校验不是认证。未来模块的权限必须明确设计，不能因同源或挂在 `/api/` 下就获得私有操作权限；需要 Webhook 等非浏览器调用时另行定义签名/授权，而不是全局取消防护。

## 8. 打包、安装与旧版本处理

- `tools/server/package.py` 继续从干净、满足 `DEPLOY_REQUIRED_REF` 的固定 Git 提交取代码，不复制工作区，不自动提交/推送。
- 产物升级为通用 Server 包：包含 `server/` 的批准 Python 包路径、固定依赖、完整 Git SHA 与逐文件摘要标记；排除测试、工具、临时数据、配置和秘密。新增业务模块不需要手工扩充 Robot 专用文件清单。
- 明确新的 manifest kind/schema 与目录布局，校验路径、常规文件类型、大小和摘要，拒绝穿越/链接/重复项；安装器从同一提交导出，不混用工作区版本。
- 静态 Artifact 与 Server Artifact 仍是两种产物，可以来自同一提交；不要改成直接同步整个仓库。`run.sh deploy` 保持静态发布职责。
- `.gitattributes`、产物验证、smoke 与开发静态规则同步处理 `server/`、`tools/server/`、`agents/`、开发环境/状态；安装源码和计划可以版本管理，但不当网页发布。
- 通用安装器使用站点级服务身份和目录布局，健康检查改为 `/api/health`；服务凭据改为真正的 API Key 来源，不再生成 Robot 配置密码。
- 复用已有安装器中的非登录账号创建、权限隔离、开机运行、异常重启、代码版本切换、健康检查失败回退和无副作用预览机制；不新增 Redis、容器编排或其他常驻辅助进程。
- 托管配置一次生成后保留，Key 和状态与 release 分开。真实 Web Server/TLS/主机配置仍在服务器，不入库；安装器不自动覆盖未知站点配置。
- 当前记录没有正式部署过旧 Robot 服务，但实施前必须核对实际情况。如已有实例，先确认旧服务、私有状态、代理路由及缓存，再制定停旧/切新/失败恢复顺序；最终不能并行遗留两套常驻服务。
- 回退以经过验收的安全发布为目标；不得为了恢复旧 Robot 功能而重新带回已经删除的真实终端桥接。代码回退不等于数据回退。

## 9. 原分阶段执行清单（暂停）

阶段描述的是实施顺序，不等于自动提交授权，也不意味着每阶段都单独上线。每个实际交付批次须可独立运行/部署。

**交付耦合：** 拆分运行包后，旧的“三文件”打包器/安装器就不再适用；删除配置密码后，旧凭据注入方式也不再适用。因此 P1–P4 默认作为一组架构迁移完成后再发布，不能提前部署中间状态。若需要拆为独立可部署提交，必须在相应提交中同步适配打包/安装/启动入口；P2 的前端删除与 API、资产校验仍须成套交付。不得以阶段编号为由发布缺少模块文件或仍传旧密码的服务包。
